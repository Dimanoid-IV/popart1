## 2. Что проверено и какие cookies обнаружены

Исследованы root layout, SiteAnalytics, PurchaseAnalytics, funnel/purchase helpers, OrderFlow, все обращения к browser storage и cookie API в `src`, зависимости и существующие legal-страницы. Проверка поведения выполнена на локальной production-сборке в Chrome.

| Механизм | Назначение | Когда используется | Срок / ограничения |
|---|---|---|---|
| `popart_visitor` | Идентификация посетителя для generation credits, защиты от злоупотреблений и привязки оплаты | Необходимые функции; не зависит от аналитики | Серверный HttpOnly, SameSite=Lax, Secure в production, до 365 дней; существующая реализация не менялась |

| `_ga`, `_ga_H52TSV34MX` | Google Analytics 4 | Только после разрешения аналитики | Код явно задаёт `cookie_expires: 34560000` — до 400 дней; браузер и tag могут ограничить срок. Это не срок хранения данных на серверах Google |
| `popart.landing.v1` в sessionStorage | Страница начала разрешённого измерения | Только после согласия | Сеанс вкладки; удаляется при отзыве / обнаружении истёкшего согласия |

В исходном коде не обнаружены Meta Pixel, Hotjar, Clarity, GTM container, рекламные теги или другие браузерные трекеры. Facebook используется как ссылка. Наличие пакета Stripe JS в dependencies не означает его загрузку: текущий OrderFlow переводит пользователя на hosted Stripe Checkout. Cookie-механизмы на странице Stripe находятся за границей текущего сайта и этой проверки.

Серверные интеграции генерации, хранения изображений, печати и уведомлений не превращались в браузерные трекеры и не менялись. Независимое содержимое production после будущей публикации нужно проверить отдельно: в этой задаче production не обновлялся.

## 3. Consent Mode v2 и порядок загрузки

При инициализации локальной очереди задаются:

```text
analytics_storage: denied
ad_storage: denied
ad_user_data: denied
ad_personalization: denied
security_storage: granted
```

`security_storage` соответствует необходимым защитным механизмам, существующим на сайте. Сам по себе этот параметр не загружает Google и не создаёт cookie генератора.

До согласия существует только локальная очередь consent-команд. Нет подключения `gtag.js`, Google config/event-команд измерения, сетевой отправки default consent или cookieless pings. Прежний безусловный Google init из root layout удалён.

После разрешения аналитики:

1. Обновляется `analytics_storage: granted`. Все три рекламных параметра остаются `denied`.
2. `ga-disable-G-H52TSV34MX` переключается в `false`.
3. До загрузки скрипта задаются очищенные URL, допустимые UTM, `send_page_view: false`, `allow_google_signals: false`, `allow_ad_personalization_signals: false`.
4. Загружается один Google tag; ручной `page_view` учитывает текущую страницу.

Конфигурация гарантированно предшествует первому событию, даже если эффект purchase выполнится раньше эффекта page_view. Загрузка или вставка tag, storage и dataLayer могут отказать без исключения, разрушающего пользовательский сценарий.

Рекламной категории в интерфейсе нет: соответствующих сервисов в приложении не найдено. «Принять все» разрешает существующую необязательную категорию аналитики.

Основание технического подхода: [Google Basic Consent Mode](https://developers.google.com/tag-platform/security/guides/consent?consentmode=basic), [отключение GA через ga-disable и рекламных функций](https://developers.google.com/tag-platform/security/guides/privacy). Сверено 15.10.2026.

## 4. Баннер и настройки

- Полная локализация ET/RU/EN; язык следует маршруту через существующий LanguageProvider.
- Баннер находится в обычном потоке над страницей. Он не фиксирован поверх заказа, не блокирует прокрутку и не требует согласия для покупки.
- «Принять все» и «Отклонить необязательные» имеют одинаковые оформление и доступность.
- «Настроить» открывает native dialog с управлением фокусом, закрытием Escape и подписанным checkbox аналитики. Без прежнего согласия checkbox выключен.
- Необходимая категория описана как всегда активная; фиктивных рекламных категорий нет.
- Постоянная кнопка настроек добавлена в footer. Поскольку у блога footer отсутствовал, в общий blog layout добавлен существующий Footer. На success доступна отдельная кнопка настроек.
- Ссылка на соответствующую языку privacy-страницу ведёт к разделу `#cookies`.

Сервер читает тот же cookie выбора и передаёт его в клиентское состояние. Поэтому сохранённый выбор не требует сначала показать, а затем автоматически убрать баннер при hydration.

## 5. Хранение, срок действия и синхронизация

Cookie содержит только `version`, `necessary`, `analytics`, `chosenAt`, `expiresAt`. Имен, email, IP и других контактных данных в нём нет. Текущая версия — 1.

Истёкшая, повреждённая или относящаяся к другой версии запись не разрешает аналитику и снова показывает баннер. Для повторного запроса после существенного изменения политики нужно увеличить `CONSENT_VERSION` вместе с обновлением текста политики. Срок — 180 дней; повторное сохранение неизменного выбора не продлевает записанный срок и не сбрасывает purchase callback.

При недоступном сохранении новый документ начинает с выключенной аналитикой. Явный выбор может действовать в памяти текущего документа; обновление страницы требует нового выбора. Отсутствие storage не ломает сайт.

Выбор синхронизируется между открытыми вкладками через BroadcastChannel; дополнительно cookie перепроверяется при focus, pageshow и изменении видимости. При отсутствии BroadcastChannel скрытая вкладка синхронизируется при возвращении к ней. Истечение срока контролируется и таймером, и проверкой перед каждым собственным событием.

## 6. Отзыв согласия

Порядок отзыва:

1. Немедленно включается `ga-disable-G-H52TSV34MX`.
2. Закрывается gate собственных событий, из ещё не обработанной очереди удаляются event-команды.
3. Обновляется consent на `denied` при всё ещё отключённом tag.
4. Удаляются собственные first-party Google Analytics cookies для root/доступных доменов и путей, sessionStorage контекст и localStorage dedup.
5. Обновляются UI и другие открытые вкладки.

Необходимый `popart_visitor`, заказы, кредиты и платёжные данные не удаляются. Недоступность одного storage не мешает очистке другого.

Уже выполненный JavaScript нельзя выгрузить из памяти браузера; блокировка отправки и проверка consent действуют и для ранее загруженного tag. На следующем полном открытии с отказом tag вообще не подключается. Проверен также медленный tag, который завершает загрузку после отзыва: cookies и запросов не появилось, старая очередь page_view не воспроизвелась.

Удаление ранее полученных Google данных не обещается. На поведение внешних расширений браузера или стороннего кода, отсутствующего в репозитории, эта реализация не распространяется.

## 7. Защита событий и purchase

| Событие | Поведение |
|---|---|
| `page_view` | Только после разрешения; текущая страница при первом согласии; один ручной view на проверенный переход App Router / refresh |
| `upload_start` | Без согласия не отправляется и не создаёт landing storage; загрузка фото продолжается |
| `checkout_start` | Без согласия переход продолжается сразу; с согласием сохраняется прежний callback и независимый fallback 1200 ms при заблокированном tag |
| `purchase` | Требует действительного согласия, серверной проверки оплаты/принадлежности/суммы и соблюдения временного условия; прежний стабильный opaque transaction_id сохранён |

На success Stripe retrieve для аналитики не выполняется без согласия. Событие допускается, только если согласие существовало до времени создания Stripe session. Это консервативное правило: согласие уже после открытия Checkout может исключить покупку из GA, даже если фактическая оплата произошла позднее. Оно предотвращает последующую отправку старой покупки после нового согласия. Граница времени Stripe имеет точность до секунды; некорректные часы клиента также могут уменьшить измеряемое число покупок.

Callback purchase записывает dedup только при всё ещё действующем том же разрешении. После отзыва или его замены запоздалый callback не восстанавливает аналитическое storage. Сохранение неизменного согласия не аннулирует callback. Повторные refresh и новая вкладка после подтверждения обработки не отправляют purchase повторно.

Блокировщики, сетевые отказы, недоступное хранилище и одновременные вкладки не позволяют обещать абсолютную доставку или exactly-once браузерного события. Приоритет — разрешение пользователя и работоспособность заказа.

Контактные поля, фото, исходный Stripe session ID и секреты в собственные события не добавлялись. Полный query/hash не передаётся; сохраняется прежний allowlist безопасных UTM. Landing определяется только с начала разрешённого измерения: досогласительные посещения задним числом не восстанавливаются.

### Повторение browser suite

Нужен уже имеющийся Playwright, указанный через `POPART_PLAYWRIGHT_PATH`; тест ничего не устанавливает. Цель разрешена только на `127.0.0.1` или `localhost`.

Для локального сервера с Stripe fixtures задать только в его процессе:

```sh
NODE_OPTIONS="--require=$(pwd)/tests/fixtures/stripe-consent.cjs" \
POPART_CONSENT_TEST_FIXTURES=1 STRIPE_SECRET_KEY=sk_test_local_fixture \
npm run start -- --hostname 127.0.0.1 --port 32148
```

`sk_test_local_fixture` — буквальный тестовый маркер, не Stripe credential. Preload отказывается работать без этого маркера и fixture-флага. Он не импортируется приложением и не создаёт публичного отладочного маршрута. Подменяется сетевой транспорт, потому что production bundle содержит SDK внутри себя.

В другом процессе:

```sh
POPART_PLAYWRIGHT_PATH=/absolute/path/to/existing/playwright \
POPART_CONSENT_TEST_FIXTURES=1 SEO_TEST_ORIGIN=http://127.0.0.1:32148 \
npm run test:consent:browser
```

## 11. Обязательная внешняя настройка GA4

По независимому аудиту от 15.10.2026: ресурс Popart `521244096`, поток `13360122178`, Measurement ID `G-H52TSV34MX`; автоматическое отслеживание history events было включено. В текущей задаче настройки не изменялись и их изменение владельцем не подтверждено.

Владелец должен выполнить:

1. Google Analytics → Admin → Data streams → поток сайта с ID `G-H52TSV34MX`.
2. Enhanced Measurement → шестерёнка → Page views → Advanced settings.
3. Отключить **только** `Page changes based on browser history events` («Изменения состояния страницы в истории браузера»).
4. Сохранить. Не выключать остальные опции без отдельной причины.
5. В DebugView после явного согласия проверить по одному page_view на начальное открытие, переход App Router, Back/Forward и refresh. Refresh — новый просмотр, а не дубль того же события.
6. Проверить upload_start и checkout_start без PII. Purchase проверять только в согласованной безопасной sandbox-среде; реальная платная операция для проверки не нужна.

Локальное отсутствие дублей в проверенном Chrome-сценарии не доказывает правильность внешней настройки всех сценариев и не отменяет этот шаг. DebugView не проверялся, поскольку тестовые collect намеренно не отправлялись в реальный GA4.
