### A1. Принадлежность Stripe session

На входном коде вызов `verifiedPurchase(paidSession, 'attacker')` возвращал покупку с суммой и товаром другого посетителя. Достаточно было получить действительный URL чужого success: перебор криптографически случайных Stripe ID не предполагается. Это позволяло раскрыть ограниченные данные транзакции и приписать её чужому браузеру. Доступа к email, фотографии или полномочия исполнить заказ этот код не давал.

Теперь success читает существующий HttpOnly `popart_visitor`; без него Stripe не вызывается. После серверного retrieve `metadata.visitorId` должен совпасть с cookie. Модель идентификации не новая: её уже используют генерация и checkout. Это проверка текущего браузера, а не полноценная авторизация аккаунта; перенос/удаление cookie приводит к отсутствию purchase, а не к выдаче чужих данных.

Входной session ID проверяется по типу, формату и длине. Секретный ключ остаётся на сервере. Клиент получает только разрешённый объект ecommerce с хешированным transaction_id.

### A2–A4. Отказоустойчивость аналитики

- `sendAnalyticsCommand` перехватывает исключения и возвращает признак постановки в очередь. Аналитика перестала быть причиной отказа загрузки или checkout.
- `checkout_start` получает `event_callback`, независимый fallback 1200 мс и защиту от повторного перехода. Блокировщик или сломанный tag не удерживают пользователя в магазине.
- Постоянная отметка purchase в localStorage создаётся после callback обработки события Google tag. При ошибке очереди in-memory блокировка снимается, поэтому можно повторить отправку.
- Callback подтверждает обработку tag, **не доставку на сервер GA4**. Абсолютная гарантия доставки браузерной аналитики невозможна при закрытии вкладки, сетевой блокировке или запрете cookies. Дедупликация на стороне GA4 опирается на неизменный transaction_id.

Регрессии сначала воспроизведены падающими тестами, затем исправлены. Unit-тесты проверяют реальные payload, состояние очереди, повторный вызов callback и повторный импорт модуля с сохранённым storage.

### A5. Атрибуция

На настоящем Google tag до исправления перехваченные collect-запросы не содержали source/medium для тестовых UTM. После исправления запросы содержали `cs=audit_source`, `cm=cpc`, а на следующей странице эти значения сохранялись.

Разрешены только `utm_source`, `utm_medium`, `utm_campaign` как короткие метки кампании. Значения с `@`, URL, query-синтаксисом и неподходящими символами отклоняются. Неизвестные параметры, session_id и email не передаются. UTM также нельзя заполнять персональными данными со стороны маркетинговых кампаний — фильтр символов не распознаёт все возможные имена или идентификаторы.

При SPA-переходе page_referrer теперь указывает на предыдущую страницу приложения, а не постоянно на исходный внешний referrer.

### A6–A7. Суммы и неизвестный контекст

Покупка проходит проверку server price для размера и `depositDiscountCents`, включая минимальную платёжную сумму 0,50 €. Отрицательный/некорректный депозит, превышение цены и несоответствие `amount_total` отклоняются. Используется фактически оплаченная сумма, а не клиентская цена.

Без корректного checkout context в sessionStorage custom `language` и `landing_page` не отправляются. Сам purchase и стандартная атрибуция GA4 сохраняются. Между независимыми вкладками sessionStorage не является надёжным каналом переноса; новый механизм хранения контекста заказа в рамках аудита не добавлялся.

Ограничения проверки:

- Реальная платная генерация, настоящий checkout и заказ не выполнялись. API генерации/credits/checkout в браузерных сценариях перехватывались.
- Новые CTA работают до выбора фото, поэтому передавать фотографию с landing не требуется. Навигация после начала OrderFlow по-прежнему может сбросить состояние — это существующее поведение, а не новый механизм сохранения заказа.
- На клиенте есть `accept="image/*"`, но строгие MIME/size-проверки загрузки не добавлены. Полноценную безопасность всего прежнего upload API этот PR не исправляет.
- Обработка ошибок генерации исследована по коду: при ошибке старта возвращается шаг размера; постоянная ошибка polling может повторяться до прежнего timeout. Этот участок не менялся.

## 4. Stripe и success

Проверены `mode=payment`, `status=complete`, `payment_status=paid`, EUR, целая положительная сумма, поддерживаемый размер, соответствие депозиту и владелец cookie. Top-up generation credits исключён. Неверный размер, неоплаченная/open session и отсутствие допустимых данных дают `null`, поэтому ложный purchase не отправляется.

| Сценарий | Поведение |
|---|---|
| Оплаченная canvas session своего браузера | Разрешён минимальный ecommerce payload |
| Чужая session / нет cookie | Payload не выдаётся; без cookie нет retrieve |
| Unpaid/open/expired session | Purchase отсутствует |
| Generation credits | Не считается покупкой холста |
| Refresh после обработки tag | localStorage подавляет повтор |
| Refresh до загрузки tag | Можно повторить отправку; transaction_id прежний |
| Две вкладки одновременно | Возможны два queued события до callback; transaction_id одинаковый, используется дедупликация GA4 |
| localStorage недоступен | Нет отказа UI; остаются in-memory и GA4 transaction_id |
| Ошибка Stripe/неверный ключ/недоступность сервиса | Исключение перехватывается, success не скрывается; ожидание retrieve ограничено 5 с |

Transaction_id — первые 32 hex-символа SHA-256 от session ID. Исходный ID, имя, email, адрес, телефон, изображения и metadata целиком не передаются клиентскому analytics-компоненту.

Страница не исполняет заказ и не изменяет базу. Fulfillment остаётся в прежнем webhook. Она сохраняет `noindex, nofollow` и отсутствие canonical.

Осталось прежнее ограничение UI: даже `/success` без оплаты показывает общее сообщение Order Successful. Оно не означает фактическое создание заказа или отправку purchase. Новый read может задержать эту страницу до timeout; оптимизация через streaming не выполнялась как отдельное изменение UX.

Stripe test environment для интеграционного платежа не использовался. Серверная проверка протестирована на безопасных fixtures, не на реальном платеже. Webhook и отправка настоящих уведомлений не вызывались.

## 5. GA4: код, реальный tag и аккаунт

### Код

Первый landing path хранится в sessionStorage одной вкладки и переживает переход landing → homepage. Он не содержит query/hash, но его срок жизни равен вкладке, а не точно 30-минутной сессии GA4. Для долгоживущей вкладки это нужно учитывать в отчётах.

### A8. Consent — блокер публикации

В репозитории нет CMP или проверки разрешения на аналитику. Получение tag, cookies и analytics storage начинается без согласия. Эстонская [Andmekaitse Inspektsioon](https://www.aki.ee/isikuandmed/kkk/interneti-ja-veebitegevused) указывает на необходимость предварительного добровольного согласия для аналитических cookies, позволяющих идентифицировать посетителя прямо или косвенно.

Владелец должен выбрать применимый способ управления согласием и подтвердить обработку cookies. Технический критерий закрытия: до согласия нет аналитических cookies и не отправляются события/не выполняются необязательные analytics storage записи; отказ и отзыв разрешения работают. Политика и поведение сайта должны совпадать.

Новая CMP, баннер и произвольная юридическая политика не добавлялись: это требует решения владельца и выходит за рамки минимального аудиторского исправления. Альтернативу с отключением всей аналитики также нельзя молча принять за владельца.

1. Открыть [проверенный веб-поток Popart](https://analytics.google.com/analytics/web/?authuser=1#/a368742577p521244096/admin/streams/table/13360122178).

4. Снять **только** флажок «Изменения состояния страницы в истории браузера» и сохранить.

## 11. Оставшиеся риски и действия владельца

1. **BLOCKER:** выбрать и согласовать consent-механизм для аналитики либо отдельно разрешить вариант без аналитики. Затем проверить реальные cookies/события до согласия, после отказа, после согласия и отзыва. Простое упоминание GA4 в privacy policy не является техническим consent gate.
2. **Обязательная внешняя настройка:** отключить проверенный флажок history events в указанном GA4 stream, затем проверить manual pageviews в DebugView. Остальные Enhanced Measurement опции без необходимости не трогать.
3. Подтвердить обещания отправки/получения, условия возвратов и финальную ET-редактуру.
4. Проверить sandbox-покупку после доступности безопасного тестового окружения и согласованной аналитики. Сейчас реальный Stripe/AI путь не исполнялся.
5. Сохранить понимание ограничений браузерной аналитики: ad blockers, concurrent tabs, удалённые cookies, недоступный storage и сетевые ошибки не дают абсолютной доставки/дедупликации.
6. Новый Stripe retrieve не имеет собственного rate limit; формат/cookie gate и timeout уменьшают поверхность, но не заменяют защиту от массовых запросов. Платежи или изменение заказа через этот GET не выполняются. Новую базу/rate-limiter в рамках аудита не внедряли.
7. Непроверенный success по-прежнему показывает общую положительную иллюстрацию; генерационный polling сохраняет прежнюю длительную обработку постоянных ошибок. Это существующие UX-ограничения, которые не следует путать с подтверждением оплаты или новой регрессией.
